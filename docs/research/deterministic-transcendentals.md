# Deterministic f64 transcendentals in TypeScript

Research for [issue #3](https://github.com/nipatiitti/luovi/issues/3), backing [ADR 0002](../adr/0002-deterministic-math-in-typescript.md) and the Determinism section of [05-separation-of-concerns](../intention/05-separation-of-concerns.md). Researched 2026-10-20.

## Recommendation

Port FDLIBM 5.3 from netlib into `core` by straight transliteration to TypeScript, the same way Java defines `StrictMath`. Use only IEEE `+ - * /`, `Math.sqrt`, exact `Math` members and 32-bit integer operations on the high and low words of each double. Leave out FMA and extended precision. The result will match a C build of FDLIBM compiled with `-ffp-contract=off` bit for bit, on every engine. A test port of `exp` did exactly that: zero differences in 500,000 inputs, and the same output on five engine builds. Expect about 3 to 5 times the cost of `Math.*`, or roughly 15 to 50 ns per call on an M1 Pro (about 90 to 150 ns for `pow` in the existing JS port). Documented accuracy is below 1 ulp for the main functions. Use the stdlib-js packages as a cross-check while porting, not as a runtime dependency. Don't use CORE-MATH, musl's `exp`/`log`/`pow` or Cephes as the base (reasons below). Ban `**` together with the `Math.*` transcendentals, and replace `Math.hypot`.

## What ECMAScript guarantees

- Basic arithmetic is exact-then-rounded. `Number::add`, `Number::multiply` and the other numeric methods are defined "according to the rules of IEEE 754-2019 binary double-precision arithmetic" and return 𝔽(exact result) ([spec, Number::multiply](https://tc39.es/ecma262/#sec-numeric-types-number-multiply), [Number::add](https://tc39.es/ecma262/#sec-numeric-types-number-add)). 𝔽 is defined as round to nearest, ties to even, "corresponds exactly to the behaviour of the IEEE 754-2019 roundTiesToEven mode" ([spec, Number value for x](https://tc39.es/ecma262/#number-value-for)). Every operation is rounded on its own, so an engine that fused a multiply and an add into an FMA would break the spec.
- `%` is exact. `Number::remainder` computes `n - d × truncate(n / d)` in real arithmetic and then applies 𝔽 ([spec](https://tc39.es/ecma262/#sec-numeric-types-number-remainder)), so angle wrapping with `%` is deterministic.
- `Math.sqrt` needs no replacement. Its last step is "Return 𝔽(the square root of ℝ(n))" ([spec, Math.sqrt](https://tc39.es/ecma262/#sec-math.sqrt)), so it is correctly rounded. Measured: 100,000 inputs hash the same on all four shells (see Measurements).
- `Math.fround` is exactly specified: it converts to binary32 with roundTiesToEven and back ([spec, Math.fround](https://tc39.es/ecma262/#sec-math.fround)). It is deterministic and irrelevant to f64 state. It matters in two places only. One is f32 data such as GPU buffers or `Float32Array` storage, which uses the same roundTiesToEven conversion ([spec, NumericToRawBytes](https://tc39.es/ecma262/#sec-numerictorawbytes)). The other is emulating binary32 arithmetic as `fround(a op b)`. That is correctly rounded for `+ - * / sqrt` because binary64 has at least 2p+2 bits for p = 24, so the double rounding is harmless (S. A. Figueroa, "When is double rounding innocuous?", ACM SIGNUM Newsletter 30(3), 1995). Nothing in the f64 core needs it.
- The transcendentals are not specified. The spec says the behaviour of `acos`, `acosh`, `asin`, `asinh`, `atan`, `atanh`, `atan2`, `cbrt`, `cos`, `cosh`, `exp`, `expm1`, `hypot`, `log`, `log1p`, `log2`, `log10`, `pow`, `random`, `sin`, `sinh`, `tan` and `tanh` "is not precisely specified here except to require specific results for certain argument values that represent boundary cases". It only recommends, "but not specified by this standard", the FDLIBM algorithms ([spec, Function Properties of the Math Object](https://tc39.es/ecma262/#sec-function-properties-of-the-math-object)). Each one returns "an implementation-approximated Number value" ([spec, implementation-approximated](https://tc39.es/ecma262/#implementation-approximated)).
- `Math.hypot` is implementation-approximated too. Its last step is "Return an implementation-approximated Number value representing the square root of the sum of squares" ([spec, Math.hypot](https://tc39.es/ecma262/#sec-math.hypot)). Measured: three different results across engines.
- The `**` operator is as unsafe as `Math.pow`. `Number::exponentiate` "returns an implementation-approximated value" ([spec](https://tc39.es/ecma262/#sec-numeric-types-number-exponentiate)). The ADR 0002 lint rule must ban `**` and `**=` as well as `Math.pow`.
- Exactly specified, so safe: `abs`, `ceil`, `floor`, `round`, `trunc`, `sign`, `min`, `max`, `sqrt`, `fround`, `f16round`, `imul`, `clz32` and `sumPrecise`. `sumPrecise` returns 𝔽 of the exact sum ([spec](https://tc39.es/ecma262/#sec-math.sumprecise)). Bun, macOS JSC and SpiderMonkey 158 have it, Node 26.1 does not.
- Decimal literals with more than 20 significant digits round in an implementation-defined way. `RoundMVResult` lets an engine either truncate after the 20th digit or round it up ([spec, RoundMVResult](https://tc39.es/ecma262/#sec-roundmvresult)). FDLIBM writes its coefficients with 21 significant digits (for example `P1 = 1.66666666666666019037e-01` in [e_exp.c](https://www.netlib.org/fdlibm/e_exp.c)). The port should write them as 17-digit round-trip literals or build them from the hex words that FDLIBM prints next to each constant.
- Bit access needs care. Typed-array byte order "is implementation-defined" ([spec, Agents, the LittleEndian field](https://tc39.es/ecma262/#sec-agents)), so the word-index choice must be computed at load time, or `DataView` used with explicit endianness. NaN bit patterns written to buffers are also implementation-chosen ([spec, NumericToRawBytes](https://tc39.es/ecma262/#sec-numerictorawbytes)), so the state hash should canonicalise NaN.

Two facts from V8's own history show that `Math.*` is a moving target, even within one engine. The commit that moved non-Chromium `sin`/`cos` to LLVM libc measured Chromium's `Math.sin` at a maximum error of 1063 ulp ("`sin` is very off; this is crbug.com/511271840"). The same commit measured Node-style builds at 1.00 ulp before the change and 0.00 ulp after it for `cos` ([7c1d2c3724](https://github.com/v8/v8/commit/7c1d2c3724)). A V8 upgrade alone can change simulation results.

## Measurements

Setup: Apple M1 Pro, macOS 27.0. Engines: Node 26.1.0 (V8 14.6.202.34-node.19), Chrome 154.0.8037.58 headless, Bun 1.3.14 (JavaScriptCore), the system `jsc` shell, and the SpiderMonkey 158.0.1 jsshell from archive.mozilla.org. Inputs: 20,000 per function, generated with a seeded `Math.imul` PRNG and bit casts, so every engine saw bit-identical arguments (checked). Domains: trig on [-10, 10] and [-1e6, 1e6]; `tan` also on [-1.5, 1.5]; `exp` on [-700, 700] and [-1, 1]; `log` log-uniform over 2^-1000 to 2^1000 plus [0.5, 2]; `pow` with x in [0.01, 100], y in [-50, 50], plus x in [0.99, 1.01], y in [0, 8700]; `asin`/`acos` on [-1, 1]; hyperbolics on [-20, 20] and [-1, 1]; `atan2`/`hypot` on [-100, 100]^2. The harness lived in a scratch directory and is not committed.

Some of stdlib-js's cost comes from how it is packaged rather than from the algorithm. Each function is a separate CommonJS module that calls helper modules such as `getHighWord`, and `cosh` is Cephes' `(exp(x) + exp(-x)) / 2`, which is two `exp` calls. To measure a lean port, `fdlibm/e_exp.c` was transliterated line by line, sharing one `Float64Array`/`Int32Array` view. Results:

|              | Math.exp | stdlib-js exp | lean FDLIBM exp |
| ------------ | -------- | ------------- | --------------- |
| Node         | 6.3 ns   | 26.2 ns       | 23.2 ns         |
| jsc          | 5.0 ns   | 22.0 ns       | 17.8 ns         |
| SpiderMonkey | 5.9 ns   | 52.5 ns       | 19.0 ns         |

The lean port matched C FDLIBM 5.3 `__ieee754_exp` (Apple clang 21, `-O2 -ffp-contract=off`) on all 500,000 test inputs. With `-ffp-contract=fast`, which lets clang fuse into FMA on arm64, the C build differed from the port on 165 inputs. Golden vectors must therefore come from a non-contracted build.

Against the performance budget: at about 25 ns per call, the 1 ms hero-boat budget covers about 40,000 transcendental calls. A model making a few thousand calls per tick spends well under 10% of its budget on them.

## Why FDLIBM 5.3 over the others

- Its accuracy is documented with an error analysis, and the measured FreeBSD-lineage ports stay below 0.86 ulp. That is in the same range as the engines' own `Math.*` for every function except `pow`, where FDLIBM's "nearly rounded" measured 0.81 ulp against the engines' 0.51.
- It is the one library whose correctness criterion is already "same bits as the reference". The ECMAScript spec recommends it, and Java has defined `StrictMath` as FDLIBM 5.3 transliterated, which shows a transliteration can reproduce the C library bit for bit. A C build of the same sources gives the port an exact oracle.
- Its integer work is 32-bit, which maps directly onto JS bitwise operators. musl's and CORE-MATH's 64-bit and 128-bit integer work does not.
- About 1,500 lines of C, comments excluded, cover `sin`, `cos`, `tan`, the two argument reducers, `atan`, `atan2`, `exp`, `expm1`, `log`, `log1p`, `log10`, `pow`, `asin`, `acos`, `sinh`, `cosh`, `tanh`, `hypot`, `cbrt` and `scalbn` (a count of the netlib files).
- It is better than depending on stdlib-js. The port pins one algorithm lineage (stdlib-js mixes FreeBSD, Cephes and Go), drops 179 transitive packages, avoids the slow `pow` and `cosh`, and cannot change through a dependency upgrade.

Correct rounding (CORE-MATH, or LLVM libc as V8 now ships) would make results independent of which library is used. That is attractive, but the port cost and runtime cost are much higher, and the simulation gains nothing from the last 0.3 ulp. Revisit only if an engine-provided correctly rounded `Math` ever becomes a spec requirement.

## Shape for `core`

- One module per FDLIBM file family, each keeping the Sun notice as the licence requires. The polynomial coefficients are part of the algorithm, not empirical model constants, so they stay in `core` with the FDLIBM file cited. This reading of the "No magic coefficients" rule is worth a one-line confirmation in ADR 0002.
- High and low words through one shared `Float64Array` and `Int32Array` view, with the word index chosen by an endianness probe at load. The lean `exp` port used this approach. FDLIBM's `(int)` casts become `| 0` and its unsigned compares become `>>> 0`.
- Golden vectors from netlib FDLIBM compiled with `-ffp-contract=off`, checked bit-exact in Node and in a browser as part of the cross-engine benchmark in ADR 0002. This falls under the `core` math exception in the "Tests are scenarios" rule.
- A lint rule in `core` and `sim-*` banning `Math.{sin, cos, tan, asin, acos, atan, atan2, sinh, cosh, tanh, asinh, acosh, atanh, exp, expm1, log, log1p, log2, log10, pow, cbrt, hypot, random}`, the `**` and `**=` operators, and `Math.sumPrecise`. `sumPrecise` itself is deterministic, but Node 26 lacks it.
- NaN canonicalised before hashing state.

## What a sailing simulation needs that FDLIBM 5.3 lacks

The netlib 5.3 file list ([index](https://netlib.org/fdlibm/index.html)) has `acos`, `acosh`, `asin`, `asinh`, `atan`, `atan2`, `atanh`, `cbrt`, `cos`, `cosh`, `erf`, `exp`, `expm1`, `fmod`, `hypot`, `lgamma`, Bessel `j0`/`j1`/`jn`, `log`, `log10`, `log1p`, `pow`, `remainder`, `sin`, `sinh`, `sqrt`, `tan` and `tanh`. Missing for this project:

- `sincos`. Rotations, quaternion slerp, wave phase and Box-Muller sampling from the seeded RNG all want sine and cosine of the same angle. Write it in `core` with one shared `__ieee754_rem_pio2` call and both kernels. Each output stays bit-identical to `sin` and `cos`, at close to the cost of one call.
- Integer powers. JONSWAP and Pierson-Moskowitz spectra use ω^-5 and ω^-4, drag and lift laws use squares and cubes. A `powInt(x, n)` by repeated squaring is deterministic and much cheaper than `pow`. It won't match `pow` bit for bit, so the code must pick one per formula.
- `log2` and `exp2`, which FDLIBM 5.3 lacks (FreeBSD added them later). They are unlikely to be needed. `log10` is in the list and is needed for the ITTC-57 friction line used by hull resistance regressions.
- `hypot` for three or more arguments, for vector norms. FDLIBM's is two-argument only. `Math.sqrt(x*x + y*y + z*z)` is deterministic and fine at sailing magnitudes. Keep the FDLIBM two-argument `hypot` where overflow safety matters.
- Angle wrapping. `x % (2 * PI)` is deterministic but reduces by the double nearest 2π. Use FDLIBM `remainder` or `rem_pio2` where exact reduction matters, for example for long-running wave phase.
