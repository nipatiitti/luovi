# A scenario starts from static equilibrium with cited constants inline, and benchmarks are static gates over a harness that reads only the public surface

A scenario is one JSON document validated by a versioned Valibot schema in `core`: a seed, an environment, simulation settings and ship instances. A ship instance names its definition, load condition, tuning and any subset of controls, and gives only a horizontal position and a yaw; heave, heel and trim come from the load condition's static equilibrium that `sim-world` already solves at load, so no run begins with a settle transient and no author types a draft. Every empirical constant a scenario carries (water density and viscosity, air density, roughness length) is a cited value in the same shape the ship definition uses, written inline, with the Baltic defaults from the `data` package applied by `sim-world` when absent; there is no preset id resolved from a registry. The input stream is versioned with the scenario, and a recording is the authored scenario plus its stream in one file. A benchmark is a module that declares its gates statically (relative, band or exact) and measures them through a harness that reaches `sim-world`'s public surface only: the state and derived buffers and a per-ship load report of what the simulation computed at load. Benchmarks are tiered: the quick tier runs on every push and in every agent batch, the full tier (the polar searches) on merges to main and nightly.

Decided by the Scenario contract and benchmark runner v1 ticket ([#11](https://github.com/nipatiitti/luovi/issues/11)) on 2026-10-22, from the ship definition ([#14](https://github.com/nipatiitti/luovi/issues/14)), ocean ([#8](https://github.com/nipatiitti/luovi/issues/8)), state ([#9](https://github.com/nipatiitti/luovi/issues/9)), deterministic math ([#7](https://github.com/nipatiitti/luovi/issues/7)) and polar benchmark ([#19](https://github.com/nipatiitti/luovi/issues/19)) decisions.

## Considered options

- Authoring the full initial attitude in the scenario: every scenario would then carry a draft and trim that the mass items already determine, and a wrong one would start the run with a bounce that looks like physics.
- Named presets for water and air constants resolved from `data` at load: the registry indirection the ship definition contract rejected, and a scenario file would no longer say what it simulates.
- Benchmarks as a scenario with one measurement and one target: the polar is fifty steady-state searches over derived scenarios, so the quartet is the gate record and the module runs the harness.
- One benchmark suite run on every change: the H-boat polars alone cost about 45 CPU-minutes and a five-boat fleet about four CPU-hours, which would make every agent batch and every pull request wait on a search.
- Benchmarks reading `sim-*` internals for load-time checks: forbidden by the repository rules; the load report carries what a benchmark needs, and the one internal equality check (basis superposition against the full product) runs inside `sim-hull` behind a scenario setting that is off by default and reports into the load report.

## Consequences

- The scenario schema is `{ version, seed, environment, settings, ships }` and nothing else: no name, no start time, no tick rate. The environment is a 10 m wind vector with an optional cited roughness length, a uniform depth, an optional wave system (absent means flat water), an optional uniform current, and optional cited water and air constants. Settings are the cloth grid default, the rig substep count and the VLM self-check flag. A ship instance may override the cloth grid and, for benchmarks that want to start displaced, the attitude.
- Yaw is the rotation about world z from east, counter-clockwise, in radians; vectors are east and north components in SI. Knots and compass headings are converted in benchmark modules and the UI, never in the schema.
- An input is a control target or a whole-block environment replacement (sea, wind or current) stamped with its applied tick. A recording validates against a `Recording` schema beside `Scenario` under the same version. Recorded state buffers and snapshots are tooling files with a JSON header beside raw doubles, never a benchmark input.
- A benchmark module exports an id, its build step, its tier, whether it runs in the browser engines, its base scenario, its gates and a measure function; an explicit index lists the modules. Gate kinds are relative (target and fractional tolerance), band (minimum and maximum) and exact (bit equality). An unsettled steady-state measurement fails its gate.
- `sim-world` exposes a typed, unversioned load report per ship: rest hydrostatics, regression inputs against their bounds, VLM derivatives and lattice sizes, the definition hash, the provenance check values and the optional basis self-check error. Benchmarks and the scenario tool read it; nothing feeds back from it.
- The harness and every driver fall under the simulation lint file set, so a driver produces identical inputs on every engine; only the command line and report code read the wall clock. The browser run bundles the harness with Vite and drives Chromium, WebKit and Firefox with Playwright on the page's main thread.
- `pnpm check` never runs a benchmark. `pnpm validate` runs the quick tier in Node; `--full` adds the polars; `--engines` adds the browsers. CI runs the quick tier with engines on every push and pull request, the full tier with engines on main and nightly.
