# Simulation in a Worker with a flat ship state buffer from day one

The simulation runs in a Web Worker from the first build, and ship state is a described layout over a Float64Array shared through a double-buffered SharedArrayBuffer, with the renderer interpolating between the two most recent ticks. Retrofitting a Worker later would mean touching every renderer read of ship state, so the flat layout is the contract now even though an object graph would be more convenient in the first weeks. The same layout serves replays (append the buffer per tick) and later networking with no serialisation step.

## Amendment, 2026-10-22

Decided by the Ship state and controls contract v1 ticket ([#9](https://github.com/nipatiitti/luovi/issues/9)), with the state needs posted there by the VLM ticket ([#16](https://github.com/nipatiitti/luovi/issues/16)) and the rig prototype ([#13](https://github.com/nipatiitti/luovi/issues/13)).

- The state buffer is complete integrator state: a simulation resumed from a buffer, its tick and the effective scenario continues bit-identically. Everything that must be restored lives in it, nothing that can be recomputed does. In v1 no module draws from the RNG per tick, so no RNG word is stored; the first module that does adds its stream's state to the layout.
- The buffer holds ship state only. The environment is scenario data: a live sea or wind edit is an input that mutates the effective scenario, and the sea is regenerated from its parameters and seed. A snapshot is the effective scenario, the tick and the state buffer.
- The layout is a pure function of each ship's definition and its resolved simulation settings (cloth grid resolution), never stored with the buffer: a header, then per ship the rigid body (world position, body-to-world unit quaternion, body-frame linear and angular velocity), the controls (target and current per control in definition order), the lag states (four per lifting surface, Wagner pair then Küssner pair), the particles (position and velocity of every rig node that moves relative to the hull and is not a cloth node), the rod segments (quaternion and angular velocity) and the coarse cloth (position and velocity per node). Rig state is in the ship body frame, as the rigging chapter solves it. Every sail in a definition is always cloth in state; there is no hoisted or furled flag.
- Inputs are a recorded stream. An input is a control input (ship, control id, absolute target) or an environment edit; it is applied at the later of its named tick and the next tick, in a canonical order within the tick, last wins on the same control, and the stream records the tick it was applied at. A replay is the scenario plus that stream re-simulated, so recorded buffers are a tooling convenience and a state contract version bump ships no migration: it invalidates recorded buffers and nothing else. Rate limits are applied by `sim-world` at the start of each tick as a linear slew of current toward target at the definition's cited rate; a running line's rest length and a pivot's angle are the current value.
- A second described-layout buffer, the derived buffer, carries what is computed from state each tick and never fed back: force and moment per force module, per-surface force, inflow angle and stall weight, line tensions, cloth triangle pressures and a hydrostatic summary. It is never hashed or recorded, so slices extend it without a version.
- Why not an output view with private state in `sim-world`: networking with client prediction and mid-run snapshots both need to resume from the buffer, and retrofitting completeness means auditing every module for hidden state. Why not the environment in the buffer: the sea description is kilobytes of regenerable data and a wind vector is one scenario field; keeping the buffer ship-only keeps the state hash about ships. Why not state migrations: scenarios and ship definitions are authored and must survive a bump; a buffer is always reproducible from them and the input stream.
